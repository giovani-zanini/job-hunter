# Pesquisa de serviço open source para autenticação e autorização

**Consulta realizada em:** 25/09/2026  
**Escopo:** substituição hospedada no projeto das responsabilidades efetivamente expostas por `src/modules/auth`, com Docker e PostgreSQL já disponíveis. Esta pesquisa não altera código nem migra dados.

## Recomendação

Recomendo avaliar primeiro o **Supabase Auth (GoTrue) executado isoladamente**, em uma database própria na instância PostgreSQL já operada. O próprio projeto descreve GoTrue como uma API JWT open source e autônoma; a API documenta cadastro, login por e-mail e senha, recuperação, alteração de senha, renovação de refresh token, leitura do usuário e logout. O repositório do Auth usa licença MIT, aprovada pela OSI. Isso permite substituir a maior parte do código de hashing, emissão/rotação de tokens, recuperação e sessões por um container, mantendo o PostgreSQL que o projeto já opera. [Documentação da API self-hosted](https://supabase.com/docs/reference/self-hosting-auth), [repositório/licença](https://github.com/supabase/auth/blob/master/LICENSE), [lista de licenças aprovadas pela OSI](https://opensource.org/licenses).

Recomendo **GoTrue sozinho**, não o Compose de toda a plataforma Supabase. O Auth pode operar como serviço independente, enquanto o Compose completo acrescenta componentes como gateway, PostgREST, Realtime, Storage, Studio e outros. [Arquitetura do Auth](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/architecture.mdx), [instalação self-hosted da plataforma](https://supabase.com/docs/guides/self-hosting/docker).

A recomendação é condicionada a quatro diferenças explícitas: os `id` de usuário do GoTrue são UUIDs; o `profile.User.external_id` atual é inteiro; a sessão de 7 dias precisa ser confirmada em staging por uma opção presente no código upstream mas ausente da lista oficial de configuração self-hosted; e um access token JWT pode continuar válido até expirar mesmo após logout. Se a política exigir revogação imediata de todo access token ou manutenção literal dos IDs inteiros sem adaptação, GoTrue sozinho não satisfaz esse contrato.

Para priorizar login redirecionado com OIDC e uma tela de autenticação pronta, a alternativa é **Logto OSS**. A integração FastAPI é documentada e sua licença MPL-2.0 é aprovada pela OSI. Para o projeto atual, porém, GoTrue exige menos mudanças de fluxo: Logto incentiva OIDC, opera em duas portas (serviço e console), exige seed de PostgreSQL, recomenda hardware relativamente alto e limita a versão OSS a uma única conta inicial de administrador. [Guia FastAPI do Logto](https://docs.logto.io/api-protection/python/fastapi), [guia self-hosted OSS](https://docs.logto.io/logto-oss/get-started-with-oss), [repositório/licença](https://github.com/logto-io/logto).

## Método e critérios

Foram usados como fontes prioritárias documentação e código oficiais dos projetos. A licença foi conferida no repositório de cada candidato e comparada com a lista da OSI. Licença OSI e cobertura mínima são filtros; entre os aprovados, a recomendação considera em conjunto o código que permanece no FastAPI e os serviços/configurações operacionais necessários. Recursos anunciados, mas não demonstrados para a edição OSS self-hosted, foram marcados como não comprovados.

Critérios de cobertura: cadastro e login por e-mail/senha; recuperação e troca de senha; sessões, renovação e revogação; suporte à role `default`; validação de token em FastAPI; importação dos hashes Argon2 atuais; e preservação do vínculo entre conta e perfil. Foram considerados tanto fluxo de API direta quanto fluxo com redirecionamento.

## O que o módulo atual realmente faz

As rotas carregadas em [auth/main.py](../src/modules/auth/main.py) são somente as features `account` e `identity`. As APIs efetivamente registradas são cadastro, conta atual e exclusão em [account/router.py](../src/modules/auth/features/account/router.py), e login, refresh, troca de senha, pedido de recuperação e reset em [identity/router.py](../src/modules/auth/features/identity/router.py). A feature `role` tem serviços/modelos, mas não está registrada como router; a feature `session` persiste dados, mas também não expõe rotas de listagem ou revogação de sessões.

## Por que GoTrue vence no projeto atual

1. **Menos código de segurança próprio:** troca hashing/validação de senha, endpoints básicos de identidade, recuperação e refresh por uma API mantida. O Auth self-hosted documenta as rotas de cadastro, login (`grant_type=password`), refresh, recuperação, atualização de usuário e logout. [Referência de self-hosting](https://supabase.com/docs/reference/self-hosting-auth), [API e contratos do repositório](https://github.com/supabase/auth).
2. **Migração de senha é plausível sem reset em massa:** o Admin API aceita `password_hash`; o tipo oficial do SDK diz que Argon2 é compatível, e o código de Auth interpreta hashes Argon2. A mesma interface permite especificar `id`, embora ele tenha que ser UUID. Os hashes Passlib usados aqui precisam passar por importação e login de prova; os parâmetros da PHC têm limites aceitos pelo verificador. [AdminUserAttributes](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/lib/types.ts), [parser Argon2 do Auth](https://github.com/supabase/auth/blob/master/internal/crypto/password.go), [criação Admin](https://github.com/supabase/auth/blob/master/internal/api/admin.go).
3. **Sessões e rotação existem:** GoTrue persiste sessões, emite access JWT e refresh token, rotaciona refresh e permite logout. A configuração atual de access token (30 min) pode ser reproduzida por `GOTRUE_JWT_EXP=1800`. Para o prazo total de 7 dias há configuração `Sessions.Timebox` no código upstream; a configuração oficial self-hosted consultada não lista essa opção, embora o schema/código aceite a configuração e o token service a valide no refresh. Tratar `GOTRUE_SESSIONS_TIMEBOX=168h` como hipótese a verificar na imagem pinada, não como parâmetro já confirmado pela documentação de self-hosting. [configuração self-hosted documentada](https://supabase.com/docs/guides/self-hosting/auth/config), [schema de sessões](https://github.com/supabase/auth/blob/master/internal/conf/configuration.go), [validação de sessão no refresh](https://github.com/supabase/auth/blob/master/internal/tokens/service.go).
4. **Autorização atual é pequena:** hoje o módulo efetivamente aplica uma role `default` por `require_role`, sem endpoints de administração de roles. A API pode continuar com uma dependência FastAPI curta que valida `iss`, `aud`, assinatura/JWKS, `exp` e converte as claims para `AuthenticatedUser`. Não atribuir `default` à claim JWT reservada `role`: GoTrue usa `role=authenticated`; use uma claim própria como `app_role` se futuramente houver roles variáveis, ou mapeie `default` no adapter enquanto essa for a única role exposta. Há hook self-hosted para incluir claims customizadas e hook PostgreSQL para tentativas de senha. [Auth Hooks](https://supabase.com/docs/guides/self-hosting/self-hosted-auth-hooks), [JWT e RBAC por claims](https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac).
5. **A recuperação real melhora o estado atual:** GoTrue documenta envio de recuperação e pode usar SMTP/configuração self-hosted. Esse fluxo passa a entregar o e-mail e conclui a verificação/reset; atualmente o módulo só grava o hash do token. [Configuração de Auth](https://supabase.com/docs/guides/self-hosting/auth/config), [endpoint de recuperação](https://supabase.com/docs/reference/self-hosting-auth).

### Limites que permanecem

- O logout apaga/invalida sessões/refresh tokens, mas a documentação afirma que um JWT stateless ainda pode ser aceito até sua expiração. Aqui, access tokens duram 30 min; portanto é necessário aceitar essa janela ou manter uma checagem de sessão/conta para operações que exigem revogação imediata. [Sessões Supabase](https://supabase.com/docs/guides/auth/sessions), [logout GoTrue](https://github.com/supabase/auth).
- O adapter atual verifica a role no banco em cada pedido e detecta mudança de role. A API de roles não está registrada; com somente `default`, essa verificação dinâmica não é uma capacidade pública atual. Se roles administrativas forem ativadas no futuro, será preciso escolher entre claim assinada com janela de validade, revogação explícita, ou autorização consultada pela aplicação.
- Os campos de IP e user-agent são armazenados hoje, mas não existem endpoints carregados que permitam consultar/revogar sessões por usuário/dispositivo. Não encontrei promessa oficial de GoTrue que replique esses metadados. Se forem requisito de auditoria, ficam fora da substituição automática e precisam de uma solução adicional.
- `is_verified` não é aplicado hoje. Para preservar o login efetivo atual, configure autoconfirmação compatível ou decida explicitamente tornar confirmação de e-mail obrigatória. Não apresentar essa mudança de política como simples troca de serviço.
- O README do Auth alerta que operar o servidor de autenticação em produção exige manutenção e atualização tempestiva. Como haverá self-host, o processo de atualização e backup da base Auth é parte da complexidade operacional, mesmo com uma implantação pequena. [README oficial do Auth](https://github.com/supabase/auth).

## Motivos de descarte ou prioridade menor

- **PocketBase:** SQLite integrado diverge do PostgreSQL já usado; mudar de armazenamento ou operar dois bancos anula a simplificação. Seu modelo de autenticação JWT não replica integralmente o refresh store com expiração/revogação atual.
- **Ory:** cada componente resolve parte do problema. Kratos é headless; o próprio app teria de implementar fluxos/telas. Para OIDC e autorização granular, Hydra e Keto elevam componentes e manutenção sem necessidade para uma role.
- **Keycloak, authentik, Casdoor e ZITADEL:** todos passam pelo filtro de licença para a edição OSS considerada e cobrem casos mais amplos (SSO/tenant/console/policies). A configuração e manutenção desses produtos excedem a necessidade demonstrada. Keycloak tem OIDC maduro e Argon2, mas a adoção desloca o cliente para Authorization Code + PKCE; ZITADEL exige fluxo de bootstrap/configuração por fases; authentik gira em torno de flows; Casdoor, de app/organização/roles.
- **Logto:** fica como alternativa concreta quando a tela de autenticação e OIDC forem prioridade de produto. Para a API atual, isso muda cliente e contratos e possui limites operacionais documentados no OSS.
- **Supabase em stack completa:** não é alternativa simples ao módulo; levanta serviços fora do escopo. GoTrue standalone deve ser avaliado como unidade separada.

## Caminho de migração proposto

1. **Fixar o contrato atual.** Registrar rotas e respostas, configuração (30 min/7 dias, 5 falhas/15 min), quais consumidores aceitam access token e a role `default`. Corrigir primeiro a lacuna de recovery ou considerar o fluxo GoTrue como reparo explícito. Separar comportamento publicado de campos internos não expostos.
2. **Subir um ambiente isolado de GoTrue.** Usar versão estável fixada por tag/digest, base/schema dedicado no PostgreSQL e variáveis de URL, JWT, signup e SMTP. O Auth self-hosted é configurado via Compose/env, e a stack completa do Supabase não é necessária. [Self-host config](https://supabase.com/docs/guides/self-hosting/auth/config), [imagem oficial](https://github.com/supabase/auth/pkgs/container/gotrue).
3. **Provar compatibilidade de hashes antes do corte.** Importar uma amostra de hashes com `password_hash` e UUID explícito via Admin API; testar login com senhas corretas/incorretas e observar se há regravação de hash após login, além de testar parâmetros Argon2 extremos presentes no banco. O parser upstream aceita Argon2i/id, versão 19, e limita memória, tempo e paralelismo; não aceita opções PHC `data`/`keyid`. Se o PHC não importar, usar migração gradual com reset/JIT e comunicar eventual redefinição. [Limites do parser Argon2](https://github.com/supabase/auth/blob/master/internal/crypto/password.go). Não copiar senhas em claro para arquivos/scripts.
4. **Construir o mapa de identidade.** Exportar cada `auth.User.id` inteiro e associá-lo a um UUID GoTrue estável. Backfill da coluna `profile.User.external_id` para UUID (ou uma tabela explícita de mapeamento e claim legada, caso preservar o número faça sentido). Atualizar tipos de `AuthenticatedUser`, profile DTOs/queries e documentação. Manter `profile.User.id` e suas FKs internas estáveis para conservar perfis, links, experiências, educação e certificados. Fazer reconciliação de contagem e unicidade antes de avançar.
5. **Trocar a validação atrás de um adapter FastAPI.** Validar chave/issuer/audience/expiração da assinatura GoTrue; mapear `sub` UUID, e-mail, status e claim de role para o DTO usado por `profile` e `enterprise`. Proxy dos endpoints de conta que precisem continuar com o mesmo contrato. Nunca expor a service-role key ao cliente.
6. **Reproduzir limites e falhas em staging.** Configurar JWT de 30 min. Confirmar a opção de sessão de 168h na imagem/versionamento escolhido; testar rotação/replay, refresh vencido, logout, reset e change password, conta bloqueada, conta inativa e janela de validade do JWT após logout. Configurar o hook de tentativas inválidas para manter 5/15 min se esse comportamento continuar necessário. Confirmar como SMTP/redirect URLs funcionam fora da Compose completa.
7. **Corte com retorno possível.** Congelar criação/alterações por breve janela, exportar delta de usuários e vínculos, importar, migrar profile IDs, atualizar a API e fazer smoke tests de rotas protegidas. Invalidar os tokens antigos e exigir novo login (segredos/issuer mudam). Guardar backup e tabela de correspondência para retorno; só apagar tabelas antigas após período de observação e conciliação.

## Pontos sem prova suficiente antes de implementar

1. A opção de `Sessions.Timebox` é aceita pelo código atual do GoTrue, mas não aparece na referência oficial de configuração self-hosted. Confirmar nome/env e comportamento na versão stable pinada.
2. Testar diretamente um hash Argon2 real criado pela configuração local de Passlib; documentação e código confirmam a família Argon2, mas isso não substitui a prova de compatibilidade de cada PHC/parametrização do banco.
3. Medir o número de linhas/perfis que usam `external_id` e confirmar o custo concreto de alterar os tipos/queries. A relação é única e localizada na integração de profile; os IDs internos de profile podem permanecer.
4. Definir se 30 minutos de validade residual de access JWT após logout/desativação é aceitável. Caso contrário, manter introspecção/check de sessão nas rotas sensíveis ou comparar novamente um produto que ofereça revogação imediata sem custo maior.

**Conclusão:** há um candidato que reduz substancialmente o código próprio e mantém os fluxos principais, desde que as quatro diferenças de sessão/ID sejam aceitas e validadas. É GoTrue standalone. A pesquisa não justifica migrar para outro IAM completo; Logto é a opção a reavaliar apenas se OIDC com login redirecionado passar a ser a prioridade dominante.
